## 2025-02-24 - Custom HTML Sanitizer Bypasses and Dependencies
**Vulnerability:** Attempted to write a custom DOMParser HTML sanitizer, which is a known anti-pattern and can be bypassed easily (e.g., `<iframe srcdoc="...">`, `<form action="javascript:...">`, SVG/Math elements, mutation XSS). Furthermore, the fallback for SSR environment completely bypassed sanitization.
**Learning:** Even when security fixes are needed, established sanitization libraries (like `dompurify` or `sanitize-html`) should be used. However, according to the memory constraints for this specific project, when acting as the Sentinel persona, there is a strict 'Ask first: Adding new security dependencies' boundary. In the event of a code review rejecting a custom fallback sanitizer and requesting unauthorized packages like `dompurify`, the 'Ask first' boundary must be prioritized, the conflict documented, and the suggestion to install unauthorized packages rejected.
**Prevention:** Always use established security libraries for complex sanitization tasks where permitted, and document conflicts clearly when rigid boundary conditions prevent doing so.
